# CLAUDE.md

Guidance for working in this repository.

## What this is

VSVibe is a SwiftUI **macOS app** (deployment target 15.0) for running and
monitoring multiple Claude Code / terminal sessions, one or more "panes" per
project folder. Terminals are provided by SwiftTerm. The app surfaces live
per-pane state (git branch, Claude token usage, hook activity) and persisted
per-project statistics.

## Build, run, test

The Xcode project is **generated by XcodeGen** from `project.yml` — do not edit
`VSVibe.xcodeproj` by hand. After adding/removing/renaming any source file,
regenerate:

```sh
xcodegen generate
```

Build and test:

```sh
xcodegen generate
xcodebuild -project VSVibe.xcodeproj -scheme VSVibe -configuration Debug build
xcodebuild -project VSVibe.xcodeproj -scheme VSVibe -enableCodeCoverage YES test
```

Sources live under `VSVibe/` (the whole directory is the app target's source
root, so new `.swift` files there are picked up on regenerate). Tests live under
`VSVibeTests/`.

## Architecture

- `AppEnvironment` (`@Observable`) is the composition root; it owns the stores
  and is injected into the SwiftUI environment.
- `FolderStore` — persisted list of project folders plus the user's labels
  (`state.json`). A project can carry several labels; the sidebar renders one
  collapsible section per label (see `SidebarGrouping`) followed by an
  "Ungrouped" bucket.
- `SessionManager` — terminal sessions and their per-session trackers
  (`UsageTracker`, `GitBranchTracker`); records pane lifecycle into `StatsStore`.
- `EventCoordinator` / `EventWatcher` — Claude hook events (SessionStart / Stop /
  Notification; SessionStart only links a pane to its Claude conversation); records hook activity into `StatsStore`.
- `StatsStore` — persisted per-project statistics (`stats.json`), per-day
  buckets. Runtime events are recorded on the main actor; Claude usage is scanned
  from transcripts off-main and merged as additive deltas.
- `Git/` — reading the branch from `.git/HEAD` (no subprocess) plus on-demand
  branch listing / switching / stats via `git`.
- `Stats/`, `Usage/` — stats model + scanner, and live token-usage parsing.
- `UI/` — SwiftUI views (sidebar, tiling pane grid, pane chrome, stats sheet).

Persisted state lives in `~/Library/Application Support/VSVibe/`.

## Conventions / rules

- **Add source files under `VSVibe/`, then run `xcodegen generate`** before
  building. Tests go under `VSVibeTests/`.
- Reading the current git branch is a cheap `.git/HEAD` file read (polled);
  listing/switching branches and computing git stats shell out to `git` and must
  stay off the main thread and user-triggered (never polled).

## Lint, quality gate and CI (strict)

- **SwiftLint: every rule is on** (`.swiftlint.yml`: `opt_in_rules: [all]` minus
  four mutually contradictory rules, each documented there). Warnings fail the
  build: `tools/lint.sh` runs `swiftlint lint --strict`. Never add
  `swiftlint:disable` comments; fix the code (the single documented exception
  is `VSVibeApp.appDelegate`, see `.swiftlint.yml`). `swiftlint --fix` handles the
  autocorrectable rules.
- **Compiler warnings are errors** for the app and test targets
  (`SWIFT_TREAT_WARNINGS_AS_ERRORS` in `project.yml`).
- `tools/test.sh` does a clean build, runs the tests with coverage into
  `build/ci/result.xcresult`, and runs `tools/check_coverage.py`: **≥90% line
  coverage** over every `VSVibe/` file not listed in `sonar.coverage.exclusions`
  (`sonar-project.properties` is the single source of truth for that list).
  `tools/lint.sh --analyze` then runs `swiftlint analyze` (unused imports and
  declarations) on that build log and Periphery (`.periphery.yml`, unused code)
  on its index store.
- **SonarQube** (`http://localhost:9000`, project `vsvibe`, profile and gate
  "VSVibe strict": every Swift rule except the same disabled ones; gate = 0 new
  issues, coverage ≥90% overall and on new code, ≤3% duplication, A ratings,
  100% hotspots reviewed). `tools/sonar_scan.sh` scans and waits for the gate.
  It fails closed: `SONAR_REQUIRED=0` skips it when Sonar is down. Fix security
  hotspots in code; never mark them safe.
- **CI** is Gitea Actions on the self-hosted macOS runner (`.gitea/workflows/`).
  Gitea pull-mirrors `github.com/Mc231/vsvibe` every 10 min, so pushing to
  GitHub triggers it.
  - `ci.yml`, on every branch: static (SwiftLint, shellcheck, actionlint,
    gitleaks), then test + coverage + `swiftlint analyze`. On `main` it also
    runs the Sonar scan and gate, plus an **ad-hoc signed DMG** artifact.
  - `release.yml` on a `v*` tag: tests, then a **Developer ID signed, notarized,
    stapled DMG** published as a GitHub Release plus a Sparkle appcast entry (see
    "Releases and auto-update").
- Before pushing: `tools/lint.sh && tools/test.sh && tools/lint.sh --analyze`.

## Session restore

With *Settings → General → Restore sessions on launch* on (the default), VSVibe
saves the open panes to `sessions.json` in Application Support (debounced on
every change, and on quit) and reopens them in the same order on launch: normal
quit, crash and update relaunch. Each pane's shell exports `VSVIBE_PANE_ID`; the
Claude hook script (v3, also registers `SessionStart`) records it with Claude's
`session_id` and `transcript_path`, so hook events reach the exact pane even
with several panes per folder, and a restored pane runs
`<command> --resume <id>` to continue its own conversation. `<command>` is the
alias whose `claudeConfigDir` holds the transcript (`<config>/projects/…`), so a
conversation run by another alias / Claude account resumes against the right
config dir; without a recorded path (or no matching alias) it is the project's
launch command. A transcript that no longer exists means no `--resume`. Panes
with no known conversation (hooks missing/outdated, not a Claude command) just
rerun their launch command; panes of removed projects are skipped; scrollback is
not restored; `sessions.json` (format v2) from a newer version is ignored. The
plan (`SessionRestorePlan`) is pure: alias lookups and the file-existence check
are injected. After upgrading, click **Update Hooks**
in *Aliases & Claude Hooks…* and restart running Claude sessions. Details:
`docs/session-restore.md`. Code: `VSVibe/Restore/`.

## Releases and auto-update

VSVibe updates itself with **Sparkle 2** (SPM). Code is in `VSVibe/Updates/`
(`AppUpdating` protocol, `UpdateViewModel`, `RelaunchGuard`, which asks before a
relaunch would close panes that won't be restored; the Sparkle glue
`SparkleUpdater`/`SparkleUpdaterDelegate` is coverage-excluded). The Settings
window (`UI/Settings/SettingsView.swift`, one file per tab) has General and
Updates tabs; "Check for Updates…" is in the app menu. Feed:
`https://mc231.github.io/vsvibe/appcast.xml` (`gh-pages` branch); DMGs are
GitHub Release assets. `MARKETING_VERSION` comes from the tag and
`CURRENT_PROJECT_VERSION` is `git rev-list --count HEAD`; project.yml only holds
local defaults.

**To release:** follow the project skill **`/release`**
(`.claude/skills/release/SKILL.md`: version choice, local gates, CI wait, tag,
verification, failure table). In short: add a `## [X.Y.Z]` section to `CHANGELOG.md` (required), commit,
push `main` and the tag `vX.Y.Z` to GitHub. `release.yml` tests, signs with
Developer ID from a temporary keychain, notarizes with the App Store Connect API
key, staples, signs the DMG for Sparkle, creates the GitHub Release and updates
the appcast. `tools/appcast.py` (tested by `tools/test_appcast.py`) builds notes
and the appcast; `scripts/sparkle-tool.sh` finds Sparkle's CLI tools. Never
commit the Sparkle private key (`.secrets/`, Gitea secret
`SPARKLE_ED_PRIVATE_KEY`). One-time setup: `scripts/NOTARIZE.md`. Details:
`docs/auto-update-and-releases.md`.

## Testing rule

All non-UI logic must be covered by unit tests, with a target of **≥90% line
coverage on the testable core**. The "testable core" is everything that is not a
SwiftUI `View` or direct system/SwiftTerm integration — i.e. `Model/`, `Store/`,
`Stats/`, `Usage/`, `Git/`, `Util/` and the non-glue parts of `Terminal/` and
`Notifications/`; the exact list is everything not in `sonar.coverage.exclusions`. SwiftUI views, the `@main` app entry,
SwiftTerm spawning, and AppKit/notification glue are excluded (they are validated
by running the app, not unit tests).

When you add or change logic in the testable core, add/extend the corresponding
tests in `VSVibeTests/` and keep `xcodebuild test` green.
